## Befunde
| Nr. | Stelle | Befund | Schwere | So nachvollziehen |
|---|---|---|---|---|
| 1 | `vite.config.ts` (`root: 'src/web'`, keine `server.fs`-Einschränkung) | Der Vite-Server unter der Adresse des Cockpits liefert ohne Anmeldung jede Datei des Projektordners über `/@fs/…` aus, auch die komplette Datenbank. Das umgeht die Anmeldung: alle Kontakte, später auch das SAP-Passwort, das laut architektur.md §11 unverschlüsselt in der Datenbank liegt. `.env` und `.env.example` sperrt Vite (403). Andere Websites können die Datei nicht lesen: Vite sendet für fremde Origins keinen CORS-Kopf, und ein fremder `Host`-Kopf ergibt 403. Erreichbar ist sie also nur von diesem Rechner aus. Die Kriterien nennen nur die Seiten S1–S9, deshalb blockiert das nicht. Es widerspricht aber dem Ziel der Story »damit niemand sonst meine Kontakte sieht«, und es wird kritisch, sobald das Cockpit erreichbar betrieben wird (architektur.md §11). | Sollte | `npm run dev`, dann ohne Anmeldung `curl -o x.sqlite http://localhost:<WEB_PORT>/@fs/<Projektpfad>/data/cockpit.sqlite` ergibt 200 und 90 112 Byte. `…/@fs/<Projektpfad>/src/server/daten/startdaten.ts` ergibt 200 mit den Namen der Ansprechpartner. |
| 2 | `src/server/dienste/zugang.ts`, `src/server/daten/reset.ts` | Die Bausteinregeln der Architektur (§3) sind verletzt. `dienste/zugang.ts` enthält SQL (`SELECT wert FROM einstellung …`, `INSERT … ON CONFLICT …`), §3 sagt aber: »dienste: kein SQL … liegt in daten«. Außerdem importiert `daten/reset.ts` aus `dienste` (`setzeAgentSchluessel`), obwohl `daten` laut §3 nur `gemeinsam` kennt. Dazu kommt: `setzeAgentSchluessel` schreibt zwei Zeilen ohne Transaktion (§9: »Schreibende Dienste laufen in einer Transaktion«). Funktional ist alles in Ordnung, aber E10-S2 (Schlüssel erneuern) baut genau hierauf auf. | Sollte | `grep -n "prepare" src/server/dienste/zugang.ts`; `grep -n "dienste" src/server/daten/reset.ts` |
| 3 | `src/server/daten/db.ts`, `transaktion()` | Die neue Hilfsfunktion kann zwei Dinge nicht, die die Architektur für spätere Stories braucht (»Schreibende Dienste laufen in einer Transaktion«, E3-S3 und E7-S3). (a) Verschachtelung: Ruft ein Dienst in einer Transaktion einen anderen Dienst mit `transaktion()` auf, scheitert das mit »cannot start a transaction within a transaction«, und die äußere Transaktion wird zurückgerollt. better-sqlite3 hatte das über Savepoints erlaubt. (b) `fn` darf laut Typ ein Promise zurückgeben. Dann wird COMMIT ausgeführt, bevor das Promise fertig ist, und ein späterer Fehler rollt nichts mehr zurück. Außerdem nutzt `ladeStartdaten` die Hilfsfunktion nicht, sondern bildet BEGIN/COMMIT/ROLLBACK ein zweites Mal von Hand nach. | Sollte | Skript mit `transaktion(db, () => transaktion(db, () => 1))`: Ausnahme »cannot start a transaction within a transaction«. `transaktion(db, async () => { await …; throw … })`: direkt danach `db.isTransaction === false`, der Fehler kommt erst nach dem COMMIT. |
| 4 | `src/server/api/zugang.ts`, Auswertung von `Authorization` | Nur `Bearer ` mit großem B wird erkannt. `Authorization: bearer <gültiger Schlüssel>` ergibt 401. Nach HTTP ist das Schema unabhängig von Groß- und Kleinschreibung. Für den Simulator und die spätere Claude-Aufgabe ist das unkritisch, solange beide `Bearer` schreiben. | Hinweis | `curl -H "Authorization: bearer demo-agent-schluessel-nur-fuer-den-prototyp" …/api/v1/agent/laufauftrag` ergibt 401. |
| 5 | Abmeldung (`@fastify/secure-session`, zustandslos) | Ein vor der Abmeldung kopiertes Sitzungs-Cookie bleibt nach der Abmeldung bis zum Ablauf gültig (Vorgabe der Bibliothek: 24 Stunden). Die Abmeldung löscht nur das Cookie im Browser. Für einen lokalen Ein-Nutzer-Prototyp ist das hinnehmbar. | Hinweis | Anmelden, Cookie sichern, abmelden, `GET /ich` mit dem gesicherten Cookie ergibt 200 `{"nutzer":"marco"}`. |
| 6 | `src/server/umgebung.ts`, `scripts/einrichten.mjs` | Fehlt `COCKPIT_SESSION_SECRET` oder ist es ungültig, nimmt der Server stillschweigend einen Zufallsschlüssel. Nach jedem Neustart (bei `tsx watch` also nach jeder Codeänderung) ist Marco dann abgemeldet. `einrichten` ergänzt die Zeile nur, wenn sie leer in `.env` steht. Eine `.env` aus der Zeit von E1-S0 bekommt weder diesen Schlüssel noch `COCKPIT_PASSWORD`. Ohne Passwort bricht der Server mit einer klaren Meldung ab. Die Übergabenotiz weist darauf hin. | Hinweis | Die Zeile `COCKPIT_SESSION_SECRET` aus `.env` entfernen, `npm run einrichten` ausführen: kein »Schlüssel … erzeugt«. |
| 7 | Tests zu #3, #4, #5 | Die Adressen für Laufauftrag, Freigabe, Kontaktversuch und Löschen gibt es noch nicht. #3 und #4 prüfen deshalb nur die Zugangsprüfung vor dem 404, #5 nur den Vorgabewert des Schemas. Das passt zu dieser Wegbereiter-Story. E2-S1, E3-S3, E4-S4 und E5-S3 sollten die Ablehnung durch den Agenten und den Besitzer »marco« über ihre echten Adressen erneut prüfen. | Hinweis | `tests/api/E1-S1.test.ts` |
| 8 | `.env.example`, `src/server/daten/reset.ts` | `COCKPIT_AGENT_KEY` ist eine neue Umgebungsvariable, die architektur.md §9 nicht nennt. Bei jedem `npm run reset` wird der Agenten-Schlüssel auf diesen Wert zurückgesetzt. Mit E10-S2 (Schlüssel erneuern) ergibt sich daraus eine Frage, die die Architektur beantworten sollte.
