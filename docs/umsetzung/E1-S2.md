# E1-S2 – Vorführdatum, Zurücksetzen und Vorführleiste: Übergabe

Branch: story/E1-S2-vorfuehrdatum (baut auf story/E1-S1-zugang auf) · Datum: 19.11.2026 · Ergebnis: Fertig

## Was gebaut wurde
`Uhr` in `src/server/anbindungen/uhr.ts` als einziger Ort für die Systemzeit; im Prototyp gilt das Vorführdatum aus der Einstellung `heute_override`. Reine Datumsrechnung (Werktage, Gültigkeit) in `src/server/regeln/datum.ts`. `setzeZurueck()` in `src/server/daten/zuruecksetzen.ts` löscht alle Fachdaten, lädt die Startdaten und setzt das Datum auf 18.11.2026; der Agenten-Schlüssel bleibt erhalten. Vorführ-Adressen `GET /sim/zustand`, `POST /sim/zuruecksetzen`, `POST /sim/datum` nur bei `COCKPIT_DEMO=1`, mit Anmeldung. Gestreifte Vorführleiste über dem Produkt mit Datum, Screen-ID, »Nächster Werktag« und »Zurücksetzen«. Ein Signal `meldeAenderung()`/`useAktualisierung()` in `src/web/aktualisierung.ts`, über das spätere Screens nach einer Vorführaktion neu laden.

## So prüft man es von Hand
1. `npm run reset`, `npm run dev`, anmelden: Die gestreifte Leiste zeigt »Datum im Dummy: 18.11.2026« und »Screen S1«.
2. »Nächster Werktag« → 19.11.2026; dreimal → 23.11.2026 (Wochenende übersprungen). Bereich wechseln → die Screen-ID in der Leiste wechselt.
3. »Zurücksetzen« → 18.11.2026.
4. Mit `COCKPIT_DEMO=0` in `.env` neu starten: keine Leiste; `/api/v1/sim/zustand` antwortet nach der Anmeldung mit 404.

## Abweichungen und neue Abhängigkeiten
- Keine neuen Abhängigkeiten.
- `tests/hilfen.ts` setzt das Vorführdatum 18.11.2026 wie `npm run reset`, damit Schnittstellentests denselben Ausgangszustand haben.

## Aufgefallen, aber nicht gebaut
- Die Leiste aktualisiert nach einer Aktion nur ihr eigenes Datum und sendet das Signal; Screens mit Daten müssen `useAktualisierung()` nutzen, sobald sie gebaut werden.
- Die Schaltfläche »Agent meldet sich« und »API gestört« ergänzt E1-S3.
