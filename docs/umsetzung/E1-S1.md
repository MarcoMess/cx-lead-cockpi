# E1-S1 – Zugang für Marco und den Agenten: Übergabe

Branch: story/E1-S1-zugang (baut auf story/E1-S0-grundgeruest auf) · Datum: 19.11.2026 · Ergebnis: Fertig

## Was gebaut wurde
Anmeldung mit dem Passwort aus `COCKPIT_PASSWORD`, verschlüsseltes Sitzungs-Cookie (`@fastify/secure-session`, Schlüssel aus `COCKPIT_SESSION_SECRET`), Abmelden. Zentrale Rollenprüfung als `onRequest`-Hook: öffentlich sind nur `GET /gesundheit`, `POST /anmeldung`, `POST /abmeldung`, `GET /ich`; Adressen unter `/api/v1/agent/` verlangen den Agenten-Schlüssel (`Authorization: Bearer …`, als SHA-256-Hash gespeichert); alles andere verlangt Marcos Sitzung, der Agent bekommt dort 403. Anmeldemaske in der Oberfläche, Navigation erst nach der Anmeldung.

## So prüft man es von Hand
1. `.env` braucht `COCKPIT_PASSWORD`, `COCKPIT_SESSION_SECRET`, `COCKPIT_AGENT_KEY` (Vorlage in `.env.example`; `npm run einrichten` erzeugt den Sitzungsschlüssel).
2. `npm run reset`, `npm run dev`, http://localhost:5173 öffnen: Anmeldemaske. Falsches Passwort → »Das Passwort stimmt nicht.« Richtiges Passwort (`cockpit-demo` aus der Vorlage) → Dashboard S1.
3. `curl -i localhost:3000/api/v1/agent/laufauftrag` → 401; mit `-H "Authorization: Bearer demo-agent-schluessel-nur-fuer-den-prototyp"` → 404 (die Adresse baut E2-S1).

## Abweichungen und neue Abhängigkeiten
- Neue Abhängigkeit `@fastify/secure-session` 8.4.2 – steht in der Architektur (Abschnitt 2).
- Der Agenten-Schlüssel kommt beim Zurücksetzen aus `COCKPIT_AGENT_KEY`; fehlt er, erzeugt `npm run reset` einen zufälligen und zeigt ihn einmal an.
- Die E1-S0-Tests melden sich jetzt zuerst an; ihr Prüfinhalt ist unverändert.
- Korrektur am Grundgerüst: Die Vite-Weiterleitung galt für alles, was mit `/api` beginnt, und erfasste dadurch auch die Datei `src/web/api.ts`. Sie gilt jetzt nur für `/api/v1`.
